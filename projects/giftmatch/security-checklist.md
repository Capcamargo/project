# Security checklist GiftMatch

## Цель

Показать, что даже учебный MVP учитывает базовые риски: приватность пользовательских данных, корректную работу авторизации, ограничение бесплатного плана, безопасное разделение публичных и приватных данных, а также минимальное разделение ролей.

## 1. Auth

- Пользователь входит через Supabase Auth.
- Сессия сохраняется между страницами.
- Личный кабинет доступен только после входа.
- Сохранение подборок требует авторизации.
- После выхода профиль и сохранения очищаются из текущего интерфейса.

## 2. Роли

В MVP используются три уровня доступа:

- `guest` — неавторизованный посетитель;
- `user` — обычный авторизованный пользователь;
- `admin` — учебная роль для просмотра агрегированных показателей MVP.

Роль хранится в `profiles.role`. По умолчанию новый профиль получает `role = 'user'`. Администратор назначается вручную через Supabase SQL Editor владельцем проекта.

## 3. Приватные данные

Приватными считаются:

- профиль пользователя;
- запросы на подбор подарков;
- рекомендации пользователя;
- сохраненные подборки;
- тарифный статус профиля.

Обычный пользователь должен видеть только собственные данные.

## 4. RLS

### `profiles`

Пользователь читает и обновляет только свой профиль. Пользователь с `role = 'admin'` может читать профили для учебной админ-сводки.

### `gift_requests`

Пользователь читает, создает, обновляет и удаляет только свои запросы. Администратор может читать агрегированные данные для dashboard.

### `gift_recommendations`

Пользователь читает, создает, обновляет и удаляет только свои рекомендации. Администратор может читать агрегированные данные для dashboard.

### `gift_presets`

Публичное чтение разрешено. Публичная запись не используется.

## 5. Admin dashboard

Файл `admin.html` — минимальная учебная админ-панель.

Она показывает:

- количество пользователей;
- количество запросов;
- количество рекомендаций;
- количество сохраненных рекомендаций;
- список публичных пресетов.

Обычный пользователь видит сообщение об отсутствии admin-роли.

## 6. Edge Functions

В Supabase активны Edge Functions:

- `giftmatch-recommendations`;
- `giftmatch-account`;
- `giftmatch-save-selection`.

Для них включен `verify_jwt = true`, поэтому функции ожидают авторизованный запрос.

## 7. Paywall

- На Free-плане действует лимит сохранений.
- После достижения лимита пользователь видит тарифный сценарий.
- Paywall появляется после того, как пользователь уже получил ценность от сервиса.
- Текущий платежный сценарий является учебной имитацией.

## 8. Тестовая активация тарифа

Для курса реализован тестовый сценарий активации. Он нужен, чтобы показать продуктовую логику:

1. пользователь выбирает тариф;
2. переходит на отдельный тестовый шаг;
3. подтверждает учебную активацию;
4. профиль получает обновленный план.

На странице тестовой активации явно указано, что это не настоящая платежная форма и реальные данные карты вводить не нужно. Для реального production-продукта нужен платежный провайдер и server-side webhook.

## 9. Что уже сделано

- RLS включен для пользовательских таблиц.
- Публичные пресеты отделены от приватных данных.
- Supabase security advisor не показывал активных security warnings при проверке.
- RLS-политики оптимизированы через `(select auth.uid())`.
- Добавлена admin-роль для учебной админ-панели.
- Реальный ввод банковских карт заменен на тестовую активацию.
- Секретные service-role ключи не должны находиться во frontend-коде.

## 10. Что желательно добавить после MVP

- Rate limit для функции рекомендаций.
- Блокировку кнопки отправки формы на время запроса.
- Серверную обработку настоящей оплаты.
- Админ-управление пресетами, если проект развивается дальше.
- Журнал ключевых событий: регистрация, подбор, сохранение, paywall, тестовая активация.

## 11. Проверочный сценарий

1. Открыть сайт как гость.
2. Проверить, что публичные пресеты видны.
3. Попробовать сохранить подборку без входа.
4. Убедиться, что сервис просит войти.
5. Войти в аккаунт.
6. Сохранить подборку.
7. Открыть кабинет и увидеть только свои данные.
8. Проверить, что после лимита Free появляется тарифный сценарий.
9. Пройти тестовую активацию тарифа.
10. Вернуться в кабинет и проверить обновленный план.
11. Открыть `admin.html` обычным пользователем и увидеть ограничение доступа.
12. Назначить `role = 'admin'` тестовому профилю и проверить админ-сводку.
